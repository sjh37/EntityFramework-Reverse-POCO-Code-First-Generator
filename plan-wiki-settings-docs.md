# Plan: one wiki article per setting

Working checklist. Tick items as they are done.

`plan.md` in this repo is the Visual Studio GUI plan and is unrelated. This file is kept here rather than in
the wiki repository because every `.md` in a GitHub wiki becomes a public page, and a working plan should not
be one.

## Why

`Settings-Reference.md` is one 1,100-line page covering 118 settings. It gives each one a type, a default and
two or three lines of prose. That is a lookup table, not documentation. Three consequences:

- **It does not show the thing people actually need**, which is what the generated code looks like before and
  after. A junior developer reading "When `true`, computed columns use `private set;`" still does not know
  whether that will break their `AutoMapper` profile.
- **It rots invisibly.** The wiki audit on 2026-08-30 found a documented setting that has never existed
  (`Settings.ForeignKeyNamingStrategy`), a helper that has never existed
  (`Settings.ApplyColumnCustomizations`), three wrong defaults, and a `ColumnIdentity` example that emits code
  which does not compile on MySQL. Prose written by reading the source drifts from the source, and nothing
  catches it.
- **Twelve settings are invisible.** They are in `Settings.cs` but not in `Database.tt`, so a user who has
  only ever read their own `.tt` file does not know they exist.

The fix is one page per setting, each anchored on **real generated output**, produced by a harness rather than
typed by hand.

## Decisions already made

Recorded so they are not relitigated mid-build.

- **One page per user-facing setting**, not grouped pages. Each gets a stable URL that `Database.tt` comments,
  the GUI's help links and search can all point at. Consistency beats the fact that a few pages will be short.
- **Every before/after snippet is generated by a harness and pasted in, never hand-written.** This is the
  whole point. Hand-written examples are what produced the errors listed above.
- **`Settings-Reference.md` survives as an index**, not as the content. It becomes a table: setting, one-line
  summary, type, default, link. That keeps its inbound links and gives people a single page to scan.
- **`Settings-Callbacks.md` likewise becomes an index** for the delegate settings, keeping its "how callbacks
  fit into the pipeline" preamble, which is genuinely useful and has no per-setting home.
- **Deep-dive pages stay and are linked from the per-setting page**, not merged into it. `Owned-Entities`,
  `JSON-column-support`, `Enum-Generation-from-Table-Data`, `Settings.OnConfiguration`, `Lazy-Loading`,
  `Spatial-Types`, `File-Scoped-Namespaces`, `Data-Annotations`, `Filtering` all cover more than one setting
  and are better as they are. The setting page gives the mechanics; the deep dive gives the scenario.
- **Page naming: `Settings.<Name>`.** `Settings.OnConfiguration` already uses this and already works.
- **British English, plain hyphens**, matching the rest of the wiki.

## Scope

118 public static members on `Settings`. They split three ways.

| Group | Count | Treatment |
|-------|-------|-----------|
| User-facing settings | ~104 | One page each |
| Read-only runtime values set by the generator | 4 | One shared page |
| Helper methods (`IsEf6()`, `EfCoreVersion()`, `DatabaseProvider()`, `SqlParameter()`, ...) | 10 | Same shared page |

Read-only runtime values: `Root`, `TemplateFile`, `FilterCount`, `DefaultConstructorArgument`. `DefaultSchema`
is read-mostly - the reader assigns it, but users legitimately read it in callbacks - so it gets a full page.

## The page template

Every page follows this shape. Deviating is allowed only where a section genuinely does not apply, and then
the section is omitted rather than padded.

```markdown
# Settings.<Name>

<One sentence. What it does, in plain English, no jargon.>

|  |  |
|--|--|
| **Type** | `bool` |
| **Default** | `false` - the value in the shipped `Database.tt` |
| **Applies to** | EF Core only / EF 6 only / both |
| **Databases** | All / SQL Server only / ... |
| **In `Database.tt`?** | Yes, line 106 / No - you must add it yourself |

## What it does

Two or three short paragraphs. Assume the reader knows C# and roughly what EF is, and knows nothing about
this generator. Explain the problem the setting solves before explaining the setting.

## Example

The examples on this page are generated from this table:

    CREATE TABLE dbo.Product (...)

### `Settings.<Name> = false` (default)

    <generated code, verbatim from the harness>

### `Settings.<Name> = true`

    <generated code, verbatim from the harness>

<One or two sentences pointing at what actually changed, in case it is not obvious.>

## When to use it

Concrete situations. "Turn this on when ..." / "Leave it alone unless ...".

## Gotchas

Interactions with other settings, provider differences, anything that silently does nothing.
Omit the section if there are none - do not invent one.

## See also

Links to related settings and to the relevant deep-dive page.
```

### Rules for the prose

- **Lead with the problem, not the mechanism.** "EF needs to know a column is generated by the database, or it
  will try to insert into it" before "this emits `.ValueGeneratedOnAdd()`".
- **No unexplained jargon on first use.** Fluent API, POCO, navigation property, reverse navigation, mapping
  table, discriminator - each gets a half-line gloss the first time it appears on a page. Pages are read
  standalone via search; do not assume the reader arrived via Home.
- **Show, then tell.** The code block comes before the explanation of the code block.
- **Second person, active voice.** "Set this to `true` when you ..." not "This setting may be set ...".
- **State the failure mode.** If a wrong value produces code that does not compile, or compiles and misbehaves
  at run time, say which, and quote the error text where it is short.

## The examples harness

This is the part that makes the whole thing trustworthy, and it is built first.

> **The harness documents itself in `Generator.Tests.Unit/DocSamples/README.md`**, and `CLAUDE.md` and
> `AGENTS.md` both point at it. That file is the durable one - when this plan is finished and deleted,
> everything needed to keep the examples working is still there.

- [x] **`DocSamples` harness** under `Generator.Tests.Unit`, or a small console app beside `BuildTT`.
      It must not need a live database.
- [x] **A fixture schema.** A hand-built `EfrpgResult` covering, in as few tables as possible: an identity PK,
      a composite PK, a computed column, a nullable and a non-nullable string with lengths, a `rowversion`, a
      column with a SQL default, a one-to-many FK, a many-to-many mapping table, a view, an enum-source table,
      a stored procedure with parameters and a result set, and a table in a non-default schema.
      `Generator.Tests.Unit/WireContract/EfrpgResult.xml` is the right *format* but far too thin (two tables);
      build a richer fixture the same way so it can be loaded with `EfrpgResultXmlReader.Read` and needs no
      tool process.
- [x] **A driver.** For a given setting and a given pair of values, reset `Settings`, apply the value, run
      `GeneratorFactory.Create(...)` with the null file manager, capture the output, and write it to
      `docs-samples/<Setting>/<value>.cs`.
- [x] **Trim to the interesting hunk.** Whole generated files are unreadable in a wiki page. The driver diffs
      the two outputs and emits the changed region plus a few lines of context, so the snippet is small and is
      guaranteed to contain the difference.
- [x] **A drift check.** An NUnit test that re-runs the harness and asserts the snippets currently pasted into
      the wiki pages still match. This is what stops the next audit finding what this one found. It needs the
      wiki checked out beside the generator repo; skip with an explicit `Assert.Ignore` when it is not, the
      way `ParallelSourceTests` used to.
- [x] Settings whose effect is not visible in generated C# - `CommandTimeout`,
      `IncludeQueryTraceOn9481Flag`, `ConnectionString` - are exempt from the harness and marked as such on
      their checklist row.

## Order of work

Do it in this order. The first two steps are what make the remaining 100 pages cheap and correct.

1. ~~**Harness and fixture.**~~ Done. `Generator.Tests.Unit/DocSamples/`, run with
   `dotnet vstest ... --TestCaseFilter:"FullyQualifiedName~DocSample"`.
2. ~~**Five pilot pages.**~~ Done - review them before step 3. The five were, chosen to stress the template in different directions:
   `Settings.UsePrivateSetterForComputedColumns` (simple bool, clear diff),
   `Settings.ElementsToGenerate` (flags enum, changes which files exist),
   `Settings.UpdateColumn` (delegate, no single before/after),
   `Settings.PrependSchemaNameForTable` (undocumented, not in `.tt`, needs its own worked example),
   `Settings.OnConfiguration` (already had a page - prove the template is not a downgrade).
   **Stop and review the five before continuing.** If the template is wrong, it is wrong 104 times.

   What the pilots settled, for the pages that follow:
   - The three-table fixture schema is enough for column-level and schema-level settings. It has no view, no
     stored procedure and no many-to-many mapping table, so those settings will need it extending.
   - `DocSampleExtractor.Section` for "what does this property look like", `Outline` for "which types get
     generated", `ChangedRegion` for "what does switching this on add or remove". Three shapes cover a lot.
   - The harness only runs in single-file mode. `Settings.GenerateSeparateFiles` and the folder settings will
     need a second mode that calls `fileManagement.Process(true)` and lists what lands on disk.
   - Every fixture that generates a sample must capture and restore static state via `StaticStateSnapshot`.
     Without it `ForeignKeyTests` passes alone and fails in a full run.
3. **The 11 undocumented settings.** Highest value per page - these are currently invisible.
4. **The delegate/callback settings** (~25). Hardest prose, needs the most care.
5. **The remaining bools, strings and enums** (~65). Mostly mechanical once the harness produces the diffs.
6. **Rewrite `Settings-Reference.md` as the index**, once the pages it links to exist.
7. **Cross-link the deep-dive pages.**
8. **Wire up the drift test in CI.**

## Status

**Done.** 118 settings across 63 pages, every one reachable from the A-Z index. Every generated code block is
produced by the harness and re-checked by `WikiSnippetDriftTests`; `SettingsPageCoverageTests` guards the
index in both directions.

Two deviations from the plan above, both taken because they make better documentation:

- **Settings that are always set together share a page.** The five class modifier settings, the two collection
  settings, the three connection string settings, the four `MultiContextAllFields*` callbacks, the read-only
  runtime values. Sixty-three pages rather than a hundred and five. The index links every setting name, so the
  reader never has to know which page a setting lives on.
- **`Settings-Reference.md` is generated**, from `Generator.Tests.Unit/DocSamples/build_index.py`, rather than
  hand-maintained.

This file can now be deleted. Everything needed to keep the pages working lives in
`Generator.Tests.Unit/DocSamples/README.md`, which `CLAUDE.md` and `AGENTS.md` both point at.
